# 退出事件对账与去重机制

## 背景

退出监听（pidfd + `sched_process_exit` 跟踪点）在以下情况下可能丢失退出
事件：事件管道满导致样本被丢弃、控制进程在事件发出前被终止、内核跟踪点
缓冲区溢出等。事件一旦缺失，已经退出的容器会在任务表中一直显示为运行中，
上层因此持续占用它的端口和名称。

对账路径定期核对任务表与实际进程，为“确认已经运行过、但没有上报退出”的
任务补发退出事件。本文只说明对账路径与正常事件路径**共用的去重机制**。

## 共用的串行出口与原子“退出已上报”标记

正常事件路径和对账路径都不直接发布事件，而是汇聚到同一个出口
`Entry.reportExit`。每个任务条目上有一个原子的“退出已上报”标记
（`exitReported`），标记的比较与翻转、以及任务向 `stopped` 阶段的转换在
同一把条目锁内完成，构成一次比较并交换（CAS）：

```text
reportExit(status, reason):
    加锁
    若 exitReported == true，或阶段已是 stopped/deleted：
        解锁，返回 published = false      # 不去重覆盖、不重复发布
    否则：
        exitReported = true
        记录退出码（或“未知”值与原因）
        阶段转换为 stopped
        解锁，返回 published = true        # 仅由胜出者发布一次事件
```

谁先完成这次状态变更，谁就负责发送退出事件：

- 正常事件先到：标记置位、记录真实退出码；随后的对账扫描看到标记已置位，
  不再补发。
- 对账先到：对账以“未知”退出码补发并置位；之后延迟到达的正常事件在 CAS
  处失败，`ReportNormalExit` 返回 `published = false`，不会发布同一次退出，
  也不会用迟到的真实退出码覆盖已经记录的“未知”值。
- 多轮对账：第一轮补发后置位，后续每一轮都在 CAS 处返回 false，补发天然
  幂等。

这同时覆盖了并发场景：对账 goroutine 与正常退出 goroutine 可以从不同线程
同时进入出口，锁与 CAS 保证每个任务最多发布一次退出事件。

## 崩溃重启后标记如何恢复

该标记是纯内存的，不做持久化。重启后依靠**状态重建**而非持久化恢复：

- 任务表从磁盘上的 bundle 状态和 BPF `exited_events` map 重建
  （见 `reload.go`、`monitor.repollingInitProcess`）。退出已上报过的任务会
  被直接重建为 `stopped` 阶段，其“已上报”语义由阶段本身表达——重建出的
  任务不可能再通过 `reportExit` 的 CAS，因此不会重复发布。
- 只有重启时确实仍在运行的任务才会被重建为 `running`，并拿到一个全新的、
  未置位的标记，继续参与正常事件与对账。

因此不需要为标记本身增加持久化写入；持久化的退出状态（BPF map）与磁盘
bundle 已经足以在重启后还原“是否退出过”这一事实。

## 补发退出码：显式“未知”，绝不用零代替

对账观察到进程已消失时，退出状态可能早已被回收，真实退出码无从得知。
此时记录的是显式的未知哨兵值 `ExitStatusUnknown`（255），并附带原因
`ReasonProcessGone`，而不是表示成功的零。正常事件路径携带真实退出码，走
同一个出口；两条路径在事件中以 `Kind`（normal / reconciled）区分。

## 阶段划分：对账只处理确认运行过的任务

任务阶段为 `created → starting → running → stopped → deleted`。只有进入过
`running`（进程被确认启动过）的任务才参与对账。任务记录已存在但进程尚未
启动时（`created`/`starting`），进程不存在属于正常现象，不构成事件缺失，
对账直接跳过。已 `deleted` 的任务在出口处被拒绝，且会从任务表移除，扫描
期间发生的删除只会让按 id 的重新查找返回“未找到”并被跳过，不会崩溃或补发。
